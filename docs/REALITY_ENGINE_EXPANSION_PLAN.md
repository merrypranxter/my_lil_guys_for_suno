# Little Guy Machine — Reality Engine Expansion Plan

## Goal

Expand the existing Little Guy Machine without turning every new idea into another "mind."

The current Little Guys are cognitive operators: they change how a song is invented. The new system adds independent operational layers that change where the lyrics believe they are, who is speaking, what kind of media/event is happening, what reality rules apply, and what state the performer/consciousness is in.

The core design rule remains:

> DO NOT BLEND EVERYTHING INTO VIBES. GIVE EACH LAYER A JURISDICTION AND MAKE THE LAYERS NEGOTIATE.

## Existing architecture observed

The current app already has:
- `LittleGuy` cognitive operators and metadata.
- multi-mind stacking.
- strict Suno output boxes: STYLE 975–999, LYRICS/CONTROL 4900–4999, CAPTION 490–499.
- star + feedback learning.
- recent musical fingerprints.
- Gemini generation with procedural fallback.

Generation currently centers on `guyIds`. This expansion should preserve that system rather than overloading `LittleGuy` with scenario/persona/state data.

## New composition stack

A generated song may use any subset of these layers:

1. **MIND** — how the song thinks. Existing Little Guys.
2. **FORMAT** — what kind of media/event is occurring: game show, workout VHS, weather forecast, hotline, menu presentation, training video, courtroom, etc.
3. **ROLE** — the speaking job: host, maître d’, psychic, travel agent, ringmaster, meteorologist, tour guide, customer-service rep, etc.
4. **WORLD** — the reality the song occupies: Hell, Saturn, parallel Earth, dream realm, interdimensional bureaucracy, alien civilization, etc.
5. **SPECIES / ORIGIN** — what the speaker is: human, reptilian, Bigfoot, Mothman, goblin, demon, crystalline alien, cephalopod intelligence, etc.
6. **VENUE** — local setting: Hell airport, alien mall, haunted supper club, Saturn fitness resort, cryptid ranger station, etc.
7. **HEADSPACE / STATE** — affective/cognitive condition: bewilderment, ecstasy, manic energy, terrified-but-professional, 37-tabs-open, aberrant salience, compulsive checking, flat affect, etc.
8. **ALTERED STATE** — operational phenomenology inspired by altered states: salvia object-eternity, DMT semantic overflow/entity reception, psychedelic recursive patterning, DXM dissociative low-bandwidth embodiment, deliriant false sobriety, nitrous revelation loop, ketamine geometric dissociation, Ambien-awake domestic dream logic, etc.
9. **TONE** — delivery surface: wholesome, sleazy late-night cable, hyper-professional, ecstatic, trashy, elegant, exhausted, aggressively cheerful, etc.

These layers are independent. A song does not need all of them.

## Jurisdictions

Each layer gets a different job so combinations create tension instead of mush.

- **MIND** governs generative reasoning and structural mutation.
- **FORMAT** governs sequence, recurring segments, turn-taking, and lyric architecture.
- **ROLE** governs diction, expertise, obligations, and what the speaker believes their job requires.
- **WORLD** governs background ontology and what is considered normal.
- **SPECIES** governs embodiment, sensory assumptions, priorities, and native reference frame.
- **VENUE** governs immediate environmental constraints and available objects/events.
- **HEADSPACE** governs attention, salience, emotional weighting, interruption, memory pressure, and behavioral tempo.
- **ALTERED STATE** governs transformations of identity, time, embodiment, perception, source attribution, semantic bandwidth, and reality testing.
- **TONE** governs delivery without being allowed to overwrite the mechanisms above.

## Anti-slop rule

A selected engine is invalid if it only contributes themed vocabulary.

Examples:
- "Hell" cannot merely add fire/brimstone words. It must change what procedures, institutions, risks, and normal assumptions exist.
- "Game show" must alter lyric form through rounds/questions/prizes/elimination/scoring or equivalent mechanics.
- "ADHD: 37 Tabs Open" must create concurrent/reappearing threads, not just say "distracted."
- "Salvia" must operationalize identity replacement, object-eternity, folding/serialization, involuntary role reassignment, or other curated mechanisms rather than just say "psychedelic."
- "Deliriant" must preserve false ordinary reality/reality-testing failure rather than turn into colorful psychedelic imagery.

## Altered-state source policy

The altered-state cards are creative phenomenology engines, not drug instructions.

Use:
- the user's Ghost Erowid vault and `merrypranxter/ghost-erowid-cosmology` as the primary creative archive;
- outside web research to verify/expand phenomenological motifs where useful;
- multiple sources when a motif is presented as characteristic rather than as the user's own canon.

Do **not** put dosage, acquisition, preparation, mixing, optimization, or administration instructions into runtime cards.

The Ghost Erowid material already contains useful operational motifs, including:
- Salvia: Wheel/Grinders, folding space, Book/page-turning, Loom, Crush, Zipper, Green Realm.
- DXM: dissociation, Flange, plateaus as distinct experiential organization, Dextroverse/Void.
- Deliriants: false ordinary reality, indistinguishable hallucination, social simulations/familiars, shadow/insect/spider motifs.
- DMT: carrier-wave/Hum, time dilation, entity contact, high-density information/download motifs.
- LSD/psychedelic material: synesthesia, tracers, ego dissolution, geometric architecture.
- additional Drive material exists for nitrous, ketamine, psilocybin, ayahuasca, 2C-B, ibogaine and related archives.

## Data model

Add a generic reusable type rather than creating a separate bespoke interface for every drawer:

```ts
export type RealityDimension =
  | 'format'
  | 'role'
  | 'world'
  | 'species'
  | 'venue'
  | 'headspace'
  | 'alteredState'
  | 'tone';

export interface RealityEngine {
  id: string;
  dimension: RealityDimension;
  name: string;
  subtitle: string;
  rule: string;
  shortExplanation: string;
  tags: string[];
  accentColor?: string;
  sourceNotes?: string[];
}
```

Generation request additions should remain backwards compatible:

```ts
realityEngineIds?: string[];
```

Saved stacks and archived runs should also retain selected reality engines.

## Runtime prompt assembly

The prompt builder should render two distinct sections:

### COGNITIVE OPERATORS
Existing Little Guys and their negotiated jurisdictions.

### REALITY ENGINES
Selected format/role/world/species/venue/headspace/altered-state/tone cards.

Then enforce:
- do not collapse engines into adjective soup;
- obey each engine's jurisdiction;
- when engines conflict, generate from the seam rather than averaging them;
- format must visibly change lyric structure when applicable;
- state must visibly change attention/selection/temporal behavior;
- altered-state cards must use mechanisms, not drug-name stereotypes;
- the musical STYLE box should be influenced indirectly by structure and performance, while the LYRICS/CONTROL box carries most scenario mechanics.

## UI concept

Create a second major drawer/panel: **REALITY ENGINE**.

Tabs/chips:
- FORMAT
- ROLE
- WORLD
- SPECIES
- VENUE
- HEADSPACE
- ALTERED
- TONE

Useful controls:
- search
- randomize one dimension
- RANDOMIZE REALITY
- lock individual dimensions before randomizing others
- clear one / clear all
- "SURPRISE ME" weighted toward non-obvious combinations
- selected-engine strip near current Mind Stack

Default behavior: zero or one selection per reality dimension. Minds remain multi-select.

Later option: allow rare dual-headspace or dual-world collisions as an advanced chaos toggle rather than making everything stackable by default.

## Feedback memory

Star feedback should save both:
- selected `guyIds`
- selected `realityEngineIds`

Future preference signals can learn things like:
- user likes workout VHS + alien worlds;
- user likes dry professional delivery under impossible conditions;
- user likes salvia identity replacement;
without forcing exact repeats.

## Working method

Do one job at a time.

For each job:
1. inspect current main;
2. make the smallest coherent set of changes;
3. keep backwards compatibility;
4. verify the affected paths;
5. commit the job;
6. report exactly what changed and what the user should pull into Google AI Studio;
7. wait for "next" before starting the following job.

The plan may evolve if implementation reveals a better boundary, but new discoveries should be added rather than silently replacing useful ideas.
